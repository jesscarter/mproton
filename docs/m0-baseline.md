# Milestone 0: baseline

Goal: get numbers for the existing ways of running Windows code on this Mac, so later mproton builds have something to beat.

Machine: MacBook Air, Apple M2 (4P+4E), 16 GB.

## Tooling (done)

- `scripts/setup.sh` downloads llvm-mingw (20261104, universal macOS) to `toolchains/` (gitignored).
- `bench/mpbench.cpp` is a small deterministic benchmark. `bench/build.sh` builds it for x86_64, i686, aarch64 and arm64ec into `bench/out/`.
  - CPU scenes: scalar FP, vectorisable FP, memcpy, locked atomics, and a plain-store message-passing ping-pong. The ping-pong's `ordering_errors` exposes broken TSO emulation.
  - D3D11 scenes (FL 11_0), `gpu11.*`: 4,000 draws per frame with a constant-buffer Map each, which measures translation overhead, plus a fullscreen ALU-heavy pixel shader. (Version 1 called these `gpu.*`; `compare.py` maps the old names.)
  - D3D12 scenes, `gpu12.*`: the same two scenes (`gpu12.drawcalls` writes each draw's constants into an upload ring and binds a root CBV), plus three **feature probes** for things Metal has no native equivalent of: `gpu12.features.gs` (geometry shader point-to-quad expansion), `gpu12.features.so` (stream output / transform feedback) and `gpu12.features.tess` (hull + domain shader tessellation). Each probe draws or streams out a known pattern, reads it back and checks it, then times 100 passes, and reports `ok` plus passes/s. A probe that fails or can't build its pipeline is reported, not fatal.
  - Raw Vulkan scenes, `vk.*`: `vk.drawcalls` (push constants per draw) and `vk.fill`, through `vulkan-1.dll` with no DXVK in between. Compared with `gpu11.*`/`gpu12.*` on the same stack, this isolates winevulkan → driver overhead from the D3D translation layer.
  - Flags: `--scenes cpu,gpu12.features,vk.fill` (names or prefixes), `--api d3d11|d3d12|vk|all` (comma list), `--d3d12-shaders dxil|dxbc`, `--note TEXT` (stored in the JSON), `--list`.
  - Shaders live in `bench/mpbench.hlsl`. D3D11 compiles them at runtime with D3DCompile as before. D3D12 uses DXIL (SM 6.0) precompiled by dxc, and Vulkan uses SPIR-V generated by dxc from the same source. Both are embedded in `bench/mpbench_shaders.h`, regenerated by `bench/gen_shaders.py` only when the HLSL changes. Precompiled DXIL keeps the bytecode identical on every stack (it doesn't depend on the Wine version's d3dcompiler). It is what current D3D12 games ship, and it is Metal Shader Converter's native input. `--d3d12-shaders dxbc` compiles SM 5.0 DXBC at runtime instead, which exercises vkd3d-proton's DXBC path.
  - Writes JSON (format version 2: adds `wine`, `host`, `note`, `args`) to `--out`. Results go in `results/`.
- `bench/compare.py a.json b.json ... [--labels A,B] [--relative]` prints a markdown table comparing any number of results files. The tables below are generated with it.
- `scripts/validate-lavapipe.sh DXVK_DIR VKD3D_PROTON_DIR` runs mpbench on Linux under Wine + DXVK + vkd3d-proton on Mesa lavapipe. It checks correctness only (see the end of this page).

Takeaway: plain Wine on macOS can't run D3D11-class games at all without DXVK, DXMT or D3DMetal. That's expected, and it confirms the graphics stack is the main work.

What the run showed:

- All D3D11, D3D12 and raw Vulkan scenes run on both x86_64 and i686 (wow64 32-bit, through 32-bit winevulkan). All three D3D12 feature probes pass with DXIL: GS (128/128 probe pixels), stream output (exact byte count and all 4,096 values), and tessellation (disk coverage, which fails as designed when the tessellation factor is 1).
- With `--d3d12-shaders dxbc`, Wine 9's own d3dcompiler (vkd3d-shader's HLSL compiler) builds the D3D11-style and stream-output shaders, but has no syntax for geometry shaders or hull/domain shaders, and can't target SM 5.1 at all. The probes report this as a per-feature FAIL with the compiler message rather than aborting, and this is why the DXBC path targets SM 5.0. Newer Wine versions should do better. The default DXIL path doesn't depend on it.
- Wine's builtin d3d12 (vkd3d, without vkd3d-proton) reports SM 5.1, so DXIL pipelines fail there. `gpu12.device` now carries a hint pointing at `--d3d12-shaders dxbc`.
- Headless gotcha: under Xvfb, Wine's XRandR path reports a 0 Hz display mode, and DXVK's dxgi divides by it on swapchain creation (an unhandled exception, after which winedbg hangs the run). The script sets `UseXRandR=N` and disables the crash dialog.
- Lavapipe's tessellator is about 50x slower per vertex once a single draw goes past about 64k domain vertices. The timed tess pass therefore uses 4 draws of 64 patches (factor 16, 131k triangles), which keeps each draw under that threshold.
